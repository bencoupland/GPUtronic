# Directives

These are Grok Bot's directives to Grok Build, one per test pass, oldest first: overnight, fourth, fifth, sixth, seventh (with the reserved-SM catch-up note), eighth, ninth (the README as a landing page for the X thread, plus a controller-engaged dyno run on the 5080 with a short Results section in the README, a Pascal governor lineage line, cleanup of the damaged clone on the box, and an "About this project" blurb on Ben's X profile; a Start here section sets the order: text-only items first, then the dyno run, then cleanup, with the X profile blurb left for Ben), and tenth (hold Z on the 5080 while a second kernel in the same process uses the SMs the loop turned off, with idle-exit on, in three phases: exit alone, guest alone, both; then, only if exit stayed in band, the 1.2 load-step run that drives Z outside the 0.08 band so the PI corrections can be measured), with a continuation of the tenth pass (merge the ninth-pass results to main if not done; find out why the guest kernel did no work beside Gold under idle-exit and fix its scheduling so freed SMs reach a second kernel at any load; then widen the integral clamp as a test setting on the full-pipe 1.2 load step, which sat on the clamp in every loaded hold; no custom drivers or per-SM sleep).

They are records of what was asked at the time. The branch names and commit hashes in them (`test-results/...`, `controller-fixes`) are where the code lived when each pass ran. All of those results branches, through `test-results/2026-10-13_full-pipe`, are now part of `main`, so the code each directive points to is in `main`'s history.

Since `b8b66e7` the project is spelled GPUtronic, and the control structs are `GPUtronicControl`, `GPUtronicHandle` and `GPUtronicConfig` in `include/gputronic.h`. The directives use those names. The `GPUTRONIC_*` environment variables are unchanged.
